# M1 device layer

Milestone M1 is the device layer: platform-tools policy, an argv process runner, scan and property reads, slot and lock rules, mode waits, and a Windows USB driver classifier. The wizard UI is later work.

Crates:

- `flashwright-core` owns the process runner, the command catalogue, timeouts, output parsers, and write tokens. `flashwright-core::wizard` is the public read, plan, and confirm API. The window state machine will move into that module later.
- `flashwright-proc` and `flashwright-device` re-export the core modules.
- `flashwright-tools` classifies platform-tools, checks a zip SHA-1, and compares adb and fastboot versions.
- `flashwright-winusb` classifies a Google USB node. Off Windows the host probe reports that the host is unsupported.
- `flashwright-plan` is gate and confirm-copy logic. It does not spawn processes.
- `flashwright-magisk` builds the patch step list. A hidden or renamed Magisk app stops with "Hidden or renamed Magisk app isn't supported yet" and writes nothing.
- `xtask check` allows `Command::new` only in `flashwright-core/src/proc/spawn.rs`.

The only public write entry point is `WizardSession::confirm_and_run`. It is valid in the review phase, mints a `WriteToken` internally, and consumes the plan. A second call fails. `dry_run` uses the same expiry and step checks, is part of the plan hash, and mints no token. Write methods stay crate-private and take `&WriteToken`. The token is `Send` and not `Sync` (`PhantomData<Cell<()>>`), and it is not `Clone`, `Copy`, `Default`, or serde.

There is no public write trait.

## What is mocked

adb and fastboot reads in the automated tests are `ScriptedRunner`. No phone is contacted. USB status is classified from fixtures. The Windows SetupAPI enumerator is compiled for the Windows target and is not run here. The real runner is exercised with copies of `echo` and `sleep` named `adb` and `fastboot`. A shell symlink and a helper named `adb-helper`, `python3`, `perl`, or `node` are refused.

## Write path

- A write without installed, hash-checked platform-tools is blocked (G21). An adb write also requires the server on port 5037 to be that same adb (G22). Neither check can be skipped. The allow-list hashes are still empty, so production writes stay off.
- `fastboot getvar` is read from stdout and stderr. The slot is the value of `current-slot`, not a substring of the output.
- Sideload keeps a 300s quiet watchdog until a `(~NN%)` line, then a 900s finalising window.
- A plan hash includes a nonce, so rebuilding the same draft produces a new hash. Confirm checks the phone again (serial, mode, and slot, fingerprint, and lock when the probe succeeds) and re-hashes input files. A failed re-check discards the plan. The same hash cannot be confirmed twice.
- `getvar`, `getvar_all`, and `state` take a validated serial and a `FastbootVar`. `build_plan` is async. `SystemRunner`, `Invocation`, and `flash_args` are crate-private. `CommandRunner::run` takes a verified executable and a catalogue command.
- `xtask check` and `xtask lint-spawn` require one spawn site. `#[allow]` and `#[expect]` of `disallowed_methods` are refused outside that site. Aliased `Command::new` is caught under `crates/`, `xtask/`, and `apps/`.

## Known gaps

- No device was available. Platform-tools 37.0.1 is the only allow-list entry (`device_tested = false`). The published zip SHA-1 is `e03e78b1d80b396f1c3358e31251cb31740e1110` (`platform-tools_r37.0.1-win.zip`). Per-file SHA-256s are empty, so writes stay gated until that entry is device-verified. Platform-tools are not bundled. T1.3, the recorded part of T1.11, and the recorded part of T4.15 stay blocked.
- Gate G20 is an acknowledgement: "A pending system update may undo root after it installs." There is no read-only OTA probe in this build, and `update_engine_client` is not shipped.
- `init_boot` without root is unverified. A failed or inconclusive `ls` falls back to `data/devices.toml`.
- The SetupAPI problem-code mapping is unverified. Phase 1 detects and explains; it does not install a driver.
- A foreign adb server exposes a host protocol number, not the SDK version. The confirmation text reports that protocol number.
- `ro.boot.verifiedbootstate` `red` is not treated as unlocked. Only `orange` is.
- Device, Magisk, and minimum-bootloader tables were empty schemas in M1. The safety checks now carry the PixelFlasher tables from commit 081286d. See `docs/disclaimer.md`. `aurora`/`eos` comes from upstream issue 325 and is marked unverified.
- A ProcMon trace was not collected.
- `exec-out` returns the full stdout buffer. The runner already streams the pipes.
- The wizard UI and its full state machine are out of this milestone. `flashwright-core::wizard` exposes phase, plan build, dry run, and confirm.
- A scripted runner does not stand in for the share locks used before a real write. Those locks run when verified platform-tools have been installed on the transport.
- Threat-model rows map to tests in this crate: token privacy (compile-fail suite), quoted catalogue argv (`golden_argv.txt`), parsers (exit 0 is not enough), timeouts, and the adb-server hash check before an adb write.
- payload-dumper-rust, the AOSP proto, and avbtool are not used.
